# 05-性能测试报告

## 1. 测试目标与口径

性能测试的核心目的是回答一个问题：**"安全护栏本身会不会成为性能瓶颈？"** 因此固定区分三条路径，
分别测量各自的开销来源：

| 路径 | 说明 |
|---|---|
| `guard_block` | 护栏决策路径：注入指令在①抗注入层短路，纯 CPU 计算，不涉及感知/推理 |
| `mcp_tool` | MCP `tools/call` 单感知工具（`system_sense`），主要开销是子进程调用 |
| `full_readonly` | 全链路只读体检：感知子进程 + mock 推理 + 十一阶段闭环 |

**固定六项指标口径**（本轮起统一，后续复测直接复用）：
1. 响应时间 P50/P90/P95/P99（毫秒，客户端闭环计时）
2. 吞吐 QPS（完成请求数 / 实际墙钟时间）
3. 错误率（HTTP≠200 或响应不可解析 / 总请求）
4. 资源占用：空载基线 + 压测中每 5s 采样 `/actuator/prometheus` 的堆内存与进程 CPU
5. 稳定性长跑：中等并发持续 10 分钟，堆内存时序判断泄漏趋势
6. 真实模型延迟（外部 API 主导，与护栏 SLA 分开报告，不混算）

采集脚本：`scripts/collect-performance-metrics.py`（Python 3.12.13，零依赖，闭环压测客户端计时）。

## 2. 三层环境矩阵

| 环境 | 状态 | 说明 |
|---|---|---|
| Windows 开发机 | 仅回归基线（历史数据，见本文档旧版本） | 感知阶段子进程调用开销显著高于 Linux，不代表目标环境性能，仅用于验证代码逻辑无阻塞性问题 |
| WSL/x86 Ubuntu | 未纳入本轮 | 如需要可用同一脚本复测 |
| **龙芯 LoongArch64 + 麒麟 V11（真机）** | **本轮实测，见下文** | 目标信创部署环境，本报告的核心数据来源 |

## 3. 执行环境

| 项目 | 值 |
|---|---|
| 执行时间 | 2026-07-19 |
| 硬件/系统 | 龙芯 LoongArch64，Kylin Linux Advanced Server V11 (Swan25) |
| 内核 | `6.6.0-32.7.v2505.ky11.loongarch64` |
| CPU/内存 | **2 vCPU** / 11Gi（可用约 5Gi） |
| JDK | OpenJDK 17.0.18 Loongson build |
| 运行模式 | provider=mock，dry-run=true（护栏净开销口径，不含外部模型网络延迟） |

> 2 vCPU 是一台较小规格的虚拟机，以下 QPS 数字应结合 vCPU 数看，不代表更大规格部署下的上限。

## 4. 阶梯并发实测结果

### 4.1 guard_block（护栏决策路径，纯 CPU）

| 并发 | 请求数 | QPS | P50 | P90 | P95 | P99 | 错误率 |
|---|---|---|---|---|---|---|---|
| 5 | 24,511 | 810.2 | 5.1ms | 10.4ms | 13.1ms | 21.2ms | 0% |
| 20 | 42,701 | 1417.3 | 11.2ms | 27.6ms | 34.8ms | 52.0ms | 0% |
| 50 | 44,942 | 1487.7 | 19.5ms | 82.2ms | 96.3ms | 138.8ms | 0% |
| 100 | 45,269 | 1499.9 | 26.9ms | 178.7ms | 199.0ms | 274.6ms | 0% |

在仅 2 vCPU 的规格下达到近 1500 QPS、零错误，护栏决策本身的 CPU 开销很低；P99 随并发上升是队列
排队效应（2 vCPU 处理 100 并发的正常现象），不是护栏逻辑本身变慢。

### 4.2 mcp_tool（MCP 单感知工具，含子进程调用）

| 并发 | 请求数 | QPS | P50 | P90 | P95 | P99 | 错误率 |
|---|---|---|---|---|---|---|---|
| 5 | 5,272 | 174.2 | 27.4ms | 37.5ms | 41.1ms | 52.2ms | 0% |
| 20 | 5,310 | 175.4 | 105.1ms | 176.7ms | 204.8ms | 278.5ms | 0% |
| 50 | 4,829 | 158.9 | 291.9ms | 521.6ms | 603.2ms | 795.6ms | 0% |

QPS 在 20 并发左右见顶（约 175），继续加压 P50 反而从 105ms 涨到 292ms——2 vCPU 下子进程 fork/exec
开销是这条路径的主要瓶颈，符合预期（单感知工具每次调用都要拉起真实子进程执行 `uname`/`uptime` 等）。

### 4.3 full_readonly（全链路只读体检，十一阶段闭环）

| 并发 | 请求数 | QPS | P50 | P90 | P95 | P99 | 错误率 |
|---|---|---|---|---|---|---|---|
| 5 | 154 | 5.0 | 987.8ms | 1107.1ms | 1160.7ms | 1368.0ms | 0% |
| 10 | 160 | 5.2 | 1902.8ms | 2192.3ms | 2279.9ms | 2356.3ms | 0% |
| 20 | 170 | 5.2 | 3756.6ms | 4366.9ms | 4458.8ms | 4615.5ms | 0% |

QPS 稳定在 ~5.2，说明 2 vCPU 已饱和（全链路每次请求要跑多个感知子进程 + 十一阶段裁决），P50 随并发
近似线性增长（987ms→1903ms→3757ms）是排队等待时间累加，**全程零错误**，服务在过载下保持稳定不崩溃、
不丢请求，只是响应变慢。

**三条路径全部 0% 错误率**，无论并发多高都没有出现失败请求，符合"安全护栏在高负载下依然可靠"的设计目标。

## 5. 资源占用

| 阶段 | 堆内存 | 进程 CPU |
|---|---|---|
| 空载基线 | 30.3 MB | ~100%（JVM 启动瞬时采样，非稳态值，见下方说明） |
| 全部压测结束后 | 348.0 MB | 19.9% |

> 空载基线的 CPU 采样恰好落在 JVM 启动/类加载阶段，不代表稳态空载 CPU；真实稳态空载 CPU 应参考
> 长跑数据或压测间隙的采样。堆内存空载 30.3MB → 压测后 348.0MB 的增长符合预期（类加载、JIT 编译、
> 连接池等运行时结构建立）。

## 6. 稳定性长跑（10 分钟）

| 指标 | 结果 |
|---|---|
| 并发 | 8（`full_readonly` 路径） |
| 总请求数 | 3,253 |
| 错误率 | 0% |
| QPS | 5.4 |
| P50 / P95 / P99 | 1455.6ms / 1815.3ms / 2018.6ms |
| 堆内存区间 | 114.0MB ~ 418.0MB |
| 堆内存尾/头均值差 | +35.3MB |

10 分钟内堆内存有约 35MB 的净增长，**不足以判定为内存泄漏**——JVM 在启动初期持续加载类、填充缓存
是正常现象，通常会在更长时间窗口后趋于平稳。若要给出"无泄漏"的确定性结论，需要更长时长（如 1 小时
以上）或更高并发的复测；本轮 10 分钟窗口下零错误、无 OOM、无明显陡增，作为阶段性结果是健康的。

## 7. 真实模型延迟（对照组，不计入护栏 SLA）

同一天用真实 DeepSeek 模型跑了 33 场景红队复测（见《04-功能测试报告》第 6 节），顺带采集了端到端延迟：

| 指标 | 结果 |
|---|---|
| P50 | 12,230.3 ms |
| P95 | 30,206.2 ms |
| 最大值 | 34,617.6 ms |
| 最小值 | 6.3 ms |

**这组数字不代表本项目的性能，代表的是 DeepSeek API 的网络+推理延迟**，被真实模型主导，与护栏净开销
无关，仅供参考。最小值 6.3ms 对应的是提示词注入在入口被拦截的场景（真短路，未调用模型），差异之大
（6.3ms vs 30+秒）恰好说明"确定性护栏"与"AI 推理"这两条路径的性能特征完全不是一回事——这也是为什么
性能报告必须区分口径，不能把真实模型的响应时间当成系统本身的 SLA 汇报。

## 8. 结论

1. **护栏决策路径**（`guard_block`）在 2 vCPU 规格下即可达到近 1500 QPS、零错误，安全校验本身不构成
   性能瓶颈。
2. **全链路路径**（`full_readonly`）的瓶颈是感知阶段的子进程调用与 2 vCPU 的算力限制，不是安全逻辑本身；
   更大规格部署或后续把感知工具并行化，预期会显著改善。
3. **三条路径、全部并发阶梯，错误率均为 0%**，服务在压测下没有出现失败或崩溃，仅响应时间随过载增长，
   这是稳定的降级方式而非故障。
4. 10 分钟长跑未发现明确内存泄漏迹象，但样本时长有限，建议后续补一轮更长时间的长跑作为最终结论。
5. 真实模型延迟必须与护栏净开销分开报告——前者受外部服务主导，后者才是本项目可以承诺的性能指标。
